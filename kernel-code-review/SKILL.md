# Linux Kernel C 代码检视

## 核心原则

1. **合规优先** — 所有检视动作映射至编码规范具体条款
2. **可审计** — 检视过程全程记录，问题可追溯
3. **实用导向** — 优先发现高危问题，过滤误报

## 调用方式

### 灵活参数

支持以下调用方式（不需要全部提供）：

| 调用方式 | 行为 |
|----------|------|
| `review <文件/目录>` | 全量检视，遍历所有 10 类规范 |
| `review <文件/目录> <类别>` | 聚焦检视，只检查指定类别 |
| `review <代码片段> <类别>` | 片段检视（原始模式） |
| `quick-scan <文件/目录>` | 快速扫描，只查红线级别问题 |

**类别关键词映射**：

| 关键词 | 参考文件 |
|--------|----------|
| 数值运算、溢出、除零、回绕 | references/01_numeric_operations.md |
| 内存、指针、空指针、野指针、UAF | references/02_memory_pointer_safety.md |
| 资源泄漏、内存泄漏、fd泄漏 | references/03_resource_management.md |
| 输入验证、用户态、copy_from_user | references/04_input_validation.md |
| 并发、锁、竞态、中断、RCU | references/05_concurrency_safety.md |
| 内核API、kmalloc、设备模型、devm | references/06_kernel_api_usage.md |
| ABI、接口兼容性、符号导出 | references/07_abi_compatibility.md |
| 字符串、格式化、strcpy | references/08_string_operations.md |
| 敏感信息、密码、硬编码 | references/09_sensitive_information.md |
| 编码规范、命名、排版、风格 | references/10_kernel_style_rules.md |
| DMA、dma_map、cache一致性 | references/06_kernel_api_usage.md（DMA章节） |

未指定类别时 → 全量检视。

## 工作流

### 模式 A：全量检视

```
1. 获取代码（读取文件/目录）
2. [可选] 运行 checkpatch.pl 自动检查风格
3. 逐类加载参考文件，按优先级检视：
   - 红线类（01数值、02内存、04输入验证）→ 最先
   - 高危类（03资源、05并发、06API）→ 其次
   - 规范类（07ABI、08字符串、09敏感、10风格）→ 最后
4. 汇总报告
```

### 模式 B：聚焦检视

```
1. 获取代码
2. 加载指定类别的参考文件
3. 只检查该类别下的规范条款
4. 输出该类别的问题
```

### 模式 C：快速扫描

```
1. 获取代码
2. 只检查红线级别问题（见下方红线清单）
3. 只输出高危问题，不检查规范类问题
```

## 红线清单（快速扫描级别）

以下问题无论上下文都必须报告：

1. **kmalloc/kzalloc/vmalloc 返回值未检查** → 空指针解引用 → 内核崩溃
2. **copy_from_user/copy_to_user 返回值未检查** → 任意地址读写
3. **中断上下文调用可能睡眠的函数** (kmalloc GFP_KERNEL, mutex_lock, msleep) → 死锁
4. **kfree 后继续使用指针（UAF）** → 任意代码执行
5. **用户态指针直接解引用** → 任意地址读写
6. **无符号整数回绕导致绕过检查** → 堆溢出
7. **有符号整数溢出** → 未定义行为
8. **除零** → 内核 Panic
9. **spin_lock 与中断上下文共享变量未用 irqsave** → 死锁
10. **DMA 地址未检查 dma_mapping_error** → 数据损坏

## 评分体系

每个问题按严重程度直接判定，不使用叠加自信值：

| 等级 | 判定条件 | 说明 |
|------|----------|------|
| **高** | 命中红线清单，或可直接导致崩溃/提权/信息泄露 | 必须修复 |
| **中** | 违反规范但需要特定条件才能触发，或防御缺失 | 建议修复 |
| **低** | 编码风格问题、潜在的可维护性问题 | 可选修复 |

**误报过滤**（排除以下情况）：
- 已在作用域其他位置有有效防御
- 上下文可证明不可能触发风险
- 内核已通过其他机制保证安全（RCU、原子变量等）
- 有 devm_ 自动资源管理

## 自动修复

对于以下常见模式，直接提供修复代码：

| 模式 | 自动修复 |
|------|----------|
| `kmalloc` 未检查返回值 | 添加 `if (!ptr) return -ENOMEM;` |
| `copy_from_user` 未检查 | 添加 `if (copy_from_user(...)) return -EFAULT;` |
| `kfree` 后未置空 | 添加 `ptr = NULL;` |
| 中断上下文用 GFP_KERNEL | 改为 GFP_ATOMIC |
| `spin_lock` 共享变量未 irqsave | 改为 `spin_lock_irqsave` |
| 无符号回绕风险 | 改为先减后比较 |

用户可以选择：
- `review --fix` — 报告 + 自动应用修复
- `review` — 只报告，不修改

## 检视分析方法

### 假设检验驱动

对每个代码段：
1. **建立假设**：H0（安全）vs H1（存在风险）
2. **收集证据**：对照规范条款，分析数据流和调用链
3. **判定**：有明确违反规范的证据 → 报告；证据不足 → 跳过

### 分析要求

- 遇到函数调用 → 搜索函数定义，分析内部逻辑
- 遇到结构体成员 → 追踪定义和运算过程
- `copy_from_user`/`copy_to_user` → 必须检查返回值
- `kmalloc`/`vmalloc` → 必须检查返回值
- `spin_lock`/`mutex` → 检查死锁风险
- DMA 操作 → 检查 map/unmap 配对和 cache 同步

## 注意事项

1. 检视前先读取对应规范文件，只按规范中的条款检查
2. 存疑问题以"存疑"标记，供用户判断
3. 问题代码引用要精确（行号 + 代码片段）
4. 区分用户态和内核态规范差异
5. 驱动代码需额外关注：设备模型、中断上下文、DMA、设备树
6. 不确定的问题宁可漏报也不要误报（误报会降低用户信任）
