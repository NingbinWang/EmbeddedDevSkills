# 代码审查技能文件 - 接口兼容性规范

本文档例举Linux C(内核与驱动)安全编码规范中ABI与接口兼容性相关条款。

## 一、接口与ABI兼容性

### 1.1 导出符号规范 (EXPORT_SYMBOL)

**【描述】**
当模块间要共享函数时，必须使用 `EXPORT_SYMBOL` 宏显式导出，否则链接期间将无法解析。对于纯内核内部API和机制，推荐使用 `EXPORT_SYMBOL_GPL` 来限制非开源外部模块的加载使用。

**【风险】**
引发模块加载时的 `"Unknown symbol"` 错误。

### 1.2 用户空间/内核空间共享结构体的布局统一

**【描述】**
所有的 `ioctl` 命令使用的参数结构体，应当：
1. 仅使用固定大小类型（如 `__u8`, `__u16`, `__u32`, `__u64`，绝对不要使用 `int` 或者指代不明宽度的类型）。
2. 在32位应用运行于64位内核 (COMPAT IOCTL) 场景下，避免使用裸指针。通常在结构体里如果必须传址，建议定义为 `__u64` 形式传输，再强转是指针。
3. 对齐处理必须考虑到内存布局一致，必要时显式填充 padding 位，避免编译器在不同架构下自动进行的补位（Padding）有差异。

**【错误代码示例】**
```c
// 这种结构体用于ioctl是不安全的
struct cmd_args {
    int id;        // 指代不明
    long val;      // 32和64位下长度不同
    void *ptr;     // 32和64位下长度不同
};
```

**【正确代码示例】**
```c
struct cmd_args {
    __u32 id;
    __u32 pad;     // 对齐
    __u64 val;
    __aligned_u64 ptr; // 这种专门为指针设计
};
```

### 1.3 ioctl 命令码向后兼容

**【描述】**
增加新的 ioctl 定义或支持，必须保留老旧的 ioctl CMD 处理，不得因为升级内核就导致老的上层应用程序不兼容，这也是 Linux 系统的基本准则之一："Don't break user-space"。不要随意修改已有命令码所绑定的结构大小和编号。定义新的命令码需使用标准的 `_IOW`, `_IOR`, `_IOWR` 宏。
